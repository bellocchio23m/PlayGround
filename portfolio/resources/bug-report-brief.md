# A written bug brief that makes a repair estimable

Use this worksheet when a form, dashboard or other workflow is blocked. A short reproducible example is more useful than a long list of possible causes.

- Affected workflow — [what the user is trying to finish]
- Starting state — [signed in / role / fictional fixture]
- Steps — [numbered, exact actions]
- Expected result — [one observable outcome]
- Actual result — [what appears instead]
- Environment — [browser / app version / relevant stack]
- Frequency — [every time / observed conditions]
- Evidence — [sanitized screenshot or short recording]
- Source access — [repository and permitted branch, arranged securely]
- Acceptance condition — [the exact result to demonstrate]

For example, “Save shows success but the record disappears after reload” defines a testable failure. “The website needs improvement” requires discovery before a price can be estimated.

Keep passwords, tokens, live customer records and production credentials out of the brief. Access can be arranged through the appropriate permission workflow after scope is understood.

The linked fictional demonstration shows a browser-local version of persistence and duplicate-submission problems. A real repair needs source review, an agreed scope, compensation, deadline and acceptance criteria. The public example establishes what can be inspected, without claiming a customer result.
